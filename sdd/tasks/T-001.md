# T-001 — Lógica de reserva

## Contexto

Es la base del flujo de reserva (RF-05, RF-06). Se hace primero y sin UI para poder probarla de forma aislada. No empieza hasta que SPEC-001 esté en `status: aprobada`.

## Cambio previsto

Crear `src/lib/reservas/` con lógica pura, sin I/O ni red:

- `reservaSchema` (Zod) y `type Reserva = z.infer<...>`.
- Normalización del teléfono (espacios, guiones, `+51`).
- `buildWhatsAppUrl(reserva, numero)` con el mensaje codificado.
- `src/config/restaurante.ts` con nombre, número, horarios y máximo de personas. Valores provisionales, marcados VERIFICAR.
- Tests Vitest en `src/lib/reservas/` o `tests/`.

## Fuera de alcance de esta tarea

- Formulario, páginas y estilos (no hay UI, por tanto no aplican check-palette ni a11y).
- Carta, inicio, contacto y navegación.
- Test e2e (llega con la tarea del formulario).

## Criterios de aceptación

| ID | Dado | Cuando | Entonces |
|---|---|---|---|
| CA-05 | Datos inválidos (vacíos, teléfono mal formado, fecha pasada, hora fuera de horario, personas fuera de rango) | Se valida con el esquema | Se rechazan con error por campo; los válidos se aceptan |
| CA-06 | Datos válidos con caracteres especiales (`&`, emojis, acentos) | Se construye el enlace | URL `https://wa.me/<número>?text=<codificado>`; el mensaje decodificado contiene todos los datos |
| CA-07 | El módulo `src/lib/reservas/` | Se revisa y se ejecuta | No usa `fetch`, `localStorage`, cookies ni cualquier I/O |
